## Recommendation: **READY FOR GOVERNMENT TECHNICAL REVIEW**
This means ready to be **reviewed**, as an unofficial prototype on demonstration data. It does **not** mean
government-approved, ready for a pilot, or ready for production. The application has no official data, no live
information and no accounts. Its Android app has not been tested on a phone. **4.0 is not publicly deployed yet.**

   demonstration from a laptop instead.

4. Decide on a code licence, or keep the wording "publicly available" rather than "open source".

## 5. Is 4.0 publicly deployed?
**No. It has not been created, so there is no public 4.0 address to test.** Creating a Render service needs the
owner's Render account.

What is ready:
- **`render.yaml`.** It describes only the new service `bengaluru-transit-planner-v4`:
  - Docker, branch `v4`, Singapore, free plan;
  - health check `/api/health`;
  - `PORT=8000`, `SEED_DEMO_FEED=1`, and `ADMIN_API_KEY` generated by Render.

  It does not describe the 3.0 service, so it cannot change it.
- **Container start script.** It listens on `PORT`. Checked locally with `PORT=8061`: the app answered, loaded the
  demo feeds and reported 4.0.0-beta.1. CI starts the container on port 10000, as Render does.
- **Exact dashboard steps.** In `docs/launch/DEPLOYMENT_GUIDE.md`: route A uses a Blueprint, route B creates the web
  service by hand.
- **Proof script.** `python scripts/verify_deployment.py <4.0 address> --v3 <3.0 address>` checks HTTPS, health, a 4.x
  version, the 4.0 page title, security headers, demo-only data, upcoming transport, routes and a journey, and that 3.0
  is still 3.0. Every line must say PASS before the address is put in any letter.

Other limits:
- **Database:** the free plan has no persistent disk, so saved routes and upcoming-transport edits are lost on
  restart. A pilot needs PostgreSQL (`DATABASE_URL`) with daily backups.
- **Error logging:** only the hosting provider's own logs; the app keeps no access log by design.

## 8. Features working on demonstration data
These are DEMO ONLY; every row is listed in document 04:
- route and stop search;
- route details;
- timetables;
- fares;
- the journey planner with interchanges;
- nearby stops;
- Metro lines and stations;
- Metro-only, bus-only and bus + Metro journeys;
- the travel assistant.

These work without official data (PASS):
- maps;
- saved routes and journeys;
- upcoming-transport statuses;
- emergency numbers;
- the four languages;
- the PWA and offline use;
- accessibility settings;
- "Delete my data";
- administration.

**New this round: upcoming transport is kept in the database and edited by administrators.** No code change is needed.
- **Each entry records:** its type, location and route, status, where the status comes from (official announcement,
  press, secondary source, estimate or demonstration), announcement date, expected start, operating date, sources,
  last verification date and a public update history.
- **The rules refuse:**
  - "Operating" without a past opening date;
  - an expected start date that is not from an official announcement;
  - any estimate or demonstration entry shown as operating.
- **Year banner.** It no longer says "Official verified data" when no verified timetable exists. It now says "No
  officially verified timetable is currently available for this selection."

## 10. Security and privacy findings
- **No high-severity finding.** Open items:
  - S5, medium: one shared admin key.
  - H1, medium: free hosting has no backups.
  - A1, medium: Android not tested on a phone.
  - S4, low: inline styles allowed by the content security policy.
- **No independent penetration test.**
- **Upcoming-transport changes:** they need the admin key and a reason, and are written to the audit log and the
  entry's public history.
- **Privacy:** no names, contacts, locations, searches or payment data are stored. Device keys are hashed. "Delete my
  data" was verified end to end. No legal review against the DPDP Act, 2023 has been done.
