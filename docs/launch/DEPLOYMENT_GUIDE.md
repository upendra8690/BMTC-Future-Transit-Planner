# Deployment guide: Bengaluru Transit Planner 4.0, a separate Render service (owner steps)

The live 3.0 service stays exactly as it is:
- name `bmtc-future-transit-planner-3-0`;
- branch `main`;
- address https://bmtc-future-transit-planner-3-0.onrender.com.

4.0 is a **new, separate** Render service, `bengaluru-transit-planner-v4`, built from branch `v4`.
- Do not change the 3.0 service's branch, settings or address.
- Do not merge `v4` into `main`.
- `render.yaml` describes only the 4.0 service, so applying it cannot change 3.0.

Creating the service needs the owner's Render account, so it cannot be done from the repository. Follow one of the two
routes below. Route A is recommended because it reads every setting from `render.yaml`.

## Route A: Blueprint (recommended, about 10 minutes)
1. Sign in at https://dashboard.render.com.
2. Click **New +** (top right), then **Blueprint**.
3. Choose the repository **upendra8690/BMTC-Future-Transit-Planner-3.0**. If it is not listed, click **Configure
   account** and give Render access to that repository.
4. **Blueprint name:** `bengaluru-transit-planner-v4`.
5. **Branch:** choose **`v4`**. This matters: `main` is 3.0.
6. Render lists the resources it found in `render.yaml`. There must be exactly **one**: the web service
   `bengaluru-transit-planner-v4`, marked as new.
   - If it also lists `bmtc-future-transit-planner-3-0`, or any change to an existing service, **stop and cancel**.
7. Click **Apply** (or **Deploy Blueprint**). Render builds the Docker image; a first build on the free plan takes
   about 5–10 minutes.
8. Open the new service:
   - **Settings → Build & Deploy → Branch** must say `v4`.
   - The address at the top of the page is usually `https://bengaluru-transit-planner-v4.onrender.com`. Render adds a
     suffix if that name is taken.

## Route B: a web service created by hand (if Blueprints are unavailable)
1. **New +** → **Web Service** → choose the repository above.
2. Fill in the form:
   - **Name:** `bengaluru-transit-planner-v4`
   - **Language / Runtime:** Docker
   - **Branch:** `v4`
   - **Region:** Singapore
   - **Instance type:** Free
3. **Advanced:**
   - **Health Check Path:** `/api/health`
   - **Dockerfile Path:** `./Dockerfile`
4. **Environment variables:**
   - `PORT` = `8000`
   - `DEMO_MODE` = `0`
   - `LOAD_COMMUNITY_METRO` = `1`
   - `ADMIN_API_KEY`: click **Generate**
5. Click **Create Web Service**.

## After either route: prove it is 4.0, and that 3.0 is unchanged
Run this on any computer with Python 3. It sends only GET requests and changes nothing:
```
python scripts/verify_deployment.py https://bengaluru-transit-planner-v4.onrender.com --v3 https://bmtc-future-transit-planner-3-0.onrender.com
```
Every line must say PASS. The script checks:
- **4.0, every mode:** HTTPS; health 200; version `4.x`; the page title "Bengaluru Transit Planner"; CSP and HSTS
  headers; the upcoming-transport entries; and an empty officially-verified journey.
- **4.0, real mode** (the public default):
  - no invented feed is served;
  - the community Namma Metro timetable is loaded and current;
  - Indiranagar to Jayanagar is planned with approximate times and no fare;
  - invented demo stops are not found.
- **4.0, demonstration mode:** the demo feeds, demo routes and a bus + Metro demo journey.
- **3.0:** health 200; still 3.0, because it has no `/api/features` endpoint (4.0 added it).

Then open the 4.0 address on a phone and walk through `government_submission_2026/12_DEMONSTRATION_GUIDE.md`.

**Record the admin key safely.** Copy `ADMIN_API_KEY` from the service's **Environment** tab into a password manager.
Never paste it into chat, email or GitHub.

**Logs.** The service's **Logs** tab shows the start-up. A line from `seed_demo_feed` means the demo data loaded.

## Environment variables
| Variable | Value | Where |
|---|---|---|
| `PORT` | `8000` (the port the container listens on) | `render.yaml` |
| `ADMIN_API_KEY` | Generated by Render | Render only |
| `DEMO_MODE` | `0`: real information only. Never set it to `1` on the public service | `render.yaml` |
| `LOAD_COMMUNITY_METRO` | `1`: load the community Namma Metro timetable if missing (the image already holds it) | `render.yaml` |
| `SEED_DEMO_FEED` | Only on a demonstration server: `0` stops it loading the demo feeds | — |
| `DATABASE_URL` | Not set (SQLite on the temporary disk). For persistence: a PostgreSQL connection string | Render only; never in Git or chat |
| `RATE_LIMIT_PER_MINUTE` | Not set (default 120) | — |

## Real mode and demonstration mode
The public service runs in **real mode**. It shows:
- the community Namma Metro timetable, as unverified real data with approximate times and no fares;
- the upcoming-transport register;
- official links and emergency numbers.

Invented demo data is never served there, even if a demo feed was loaded.

For development or a presentation, run a separate **demonstration server**, which shows a banner on every screen:
- **Locally:** `DEMO_MODE=1 sh scripts/container_start.sh`, or with Docker, `docker run -p 8000:8000 -e DEMO_MODE=1 <image>`.
- **On Render:** only as a *separate* service that the owner creates, never by changing the public service.

## Updating upcoming-transport entries (no code change)
1. Open **Administration** on the 4.0 site and sign in with the admin key.
2. In **Upcoming transport entries**, choose an entry, or "Add a new entry".
3. Change the status, dates or sources, and give a reason. The change is refused if:
   - it would show a service as operating without its opening date;
   - it gives an expected start date that did not come from an official announcement.
4. Every change is shown publicly in that entry's update history.

On the free plan the database is reset on restart, so the entries return to the checked list; for lasting changes, set
`DATABASE_URL`.

## Persistence (before any pilot; not needed for the demo)
The free disk is erased on every restart.
1. Create a PostgreSQL database, for example Neon in the Singapore region.
2. Put its connection string in `DATABASE_URL` on Render.
3. Run `python scripts/migrate_database.py` once from the Render shell.

## Android APK for 4.0 (only after approval)
A push to `v4` only **compile-checks** the Android shell. It never publishes.

To publish the `app-v4-preview` pre-release, and only once its owner has approved:
1. In GitHub, add a variable under **Settings → Secrets and variables → Actions → Variables**: `V4_PLANNER_URL` = the
   4.0 address.
2. Open **Actions → Android APK → Run workflow**, choose branch `v4`, tick **publish_v4_preview**, and run it.
3. Install it on a real phone and record the model, Android version, date and results. Only then describe it as
   tested.

## Continuous integration
`ci.yml` runs lint, migrations and pytest on Python 3.12 and 3.13. It then builds the Docker image and starts it on
port 10000 with `PORT=10000`, as Render does, and checks:
- health;
- a 4.x version and the page title;
- the upcoming-transport entries and data status;
- a bus + Metro plan;
- a refused payment;
- the CSP header.

## Rollback
Render → the 4.0 service → **Events** → roll back to the previous deploy. 3.0 is never affected.
