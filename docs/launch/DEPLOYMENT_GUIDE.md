# Deployment guide — 4.0 staging (owner steps)

The live 3.0 site (`bmtc-future-transit-planner-3-0.onrender.com`, branch `main`) stays as it is. 4.0 is deployed as
a **separate** Render service from branch `v4`. Do not merge `v4` into `main`.

## 1. Create the 4.0 staging service (about 10 minutes)
1. Render dashboard → **New → Blueprint**.
2. Choose the repository `BMTC-Future-Transit-Planner-3.0` and branch **`v4`**. Render reads `render.yaml`.
3. Confirm the service `bengaluru-transit-planner-4-staging`: Docker, free plan, region Singapore, health check
   `/api/health`.
4. `ADMIN_API_KEY` is generated by Render. Copy it from the service's Environment tab into a password manager. Never
   paste it into chat or GitHub.
5. Wait for the first deploy, then check:
   - `https://<service>.onrender.com/api/health` → `{"status":"ok", ...}`
   - `https://<service>.onrender.com/api/meta` → `"version":"4.0.0-beta.1"`
   - Open the site on a phone: Home, Plan (try "Demo Lake View" to "Demo Metro Hub" with "Unverified feed"),
     Upcoming transport, Travel assistant, Data and providers.
6. Logs: the service's Logs tab. A line `seed_demo_feed` means the demo data loaded.

## 2. Environment variables
| Variable | Value | Where |
|---|---|---|
| `ADMIN_API_KEY` | Generated by Render | Render only |
| `SEED_DEMO_FEED` | `1` | `render.yaml` |
| `DATABASE_URL` | Not set (SQLite on the temporary disk). For persistence: the Neon connection string | Render only — never in Git or chat |
| `CORS_ORIGINS` | Not set | — |
| `RATE_LIMIT_PER_MINUTE` | Not set (default 120) | — |

## 3. Persistence (before any pilot, not needed for the demo)
The free disk is erased on every restart, so saved routes are lost. For a pilot, create a Neon Postgres database
(region Singapore), put its connection string in `DATABASE_URL` on Render, and run `python scripts/migrate_database.py`
once from the Render shell.

## 4. Android APK for 4.0
1. GitHub → Settings → Secrets and variables → Actions → **Variables** → New variable `V4_PLANNER_URL` = the
   staging URL from step 1.
2. Push to `v4` (or re-run the "Android APK" workflow). It publishes the `app-v4-preview` pre-release.
3. Install it on a real phone and record the model, Android version, date and results. Only then describe it as
   tested.
4. For a signed release build, follow `docs/4.0/DEPLOYMENT_AND_RELEASE_4_0.md` (signing key and secrets).

## 5. Continuous integration
`ci.yml` runs lint, migrations and pytest on Python 3.12 and 3.13. It also builds the Docker image, starts it with
the demo feed, and checks health, features, upcoming transport, data status, a bus + Metro plan, a refused payment
and the CSP header.

## Rollback
Render → the staging service → Events → roll back to the previous deploy. In Git, the checkpoint before this release
is tag `checkpoint-pre-launch-2026-11-17`.
